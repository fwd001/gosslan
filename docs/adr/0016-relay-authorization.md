## 1. Context

多跳转发今天对**所有**信封无条件执行：`handle_gossip` 第 4 步 `choose_fanout(fanout=4)`
+ TTL 衰减，任何通过验签的邻居都能让本机替它传话。同时仓库里还有一个**死开关**
`MeshRouter::relay_enabled`（默认 false、生产从不调用）：代码里"能在"、运行时"永远不在"，
是最容易误导后来者的状态。

两个具体问题：
1. **不可控**：用户无法表达"别拿我当免费中转"（流量/电量/隐私都不是零成本）。
2. **语义双份**：真正在跑的转发与那个死开关是两套说法。

## 2. Decision

1. 引入**本机策略** `relay_policy ∈ {off, friends, allowlist, all}`（settings 表，
   JSON 白名单复用同一张表），在**唯一**的转发落点（`handle_gossip` 第 4 步）生效。
   收敛掉死开关：`off` 就是那个开关"本来想说"的状态。
2. **默认 `all` ＝ 与今天逐字节一致**。理由（写下来供复核）：
   - 跨跳投递（A—B—C，A 与 C 无直连）**依赖**中间节点转发。默认改成 `off`/`friends`
     会让已有拓扑静默丢消息 —— 直接违反红线 #3，也违背用户"现有局域网聊天不能搞坏"；
   - "防止被滥用"的诉求由**用户显式选择**满足（设置 → 网络 → 中继），
     而不是由我们替所有人决定一个会破坏连通性的默认值。
3. **授权判据只读本机事实**：发送者身份取自**已验签信封**的 `sender_id`
   （`gossip.verify_envelope` 在转发之前就已通过），绝不读远端自报的"我愿中继"。
4. 判据集中在纯函数 `mesh::relay_policy::{should_forward, decide_forward}`：
   - `is_target` ⇒ 不转发（定向帧到达目的地只消费，避免回环）；
   - `ttl <= 1` ⇒ 不转发；
   - `sender_is_me` ⇒ 永远转发（源发不是中转，`off` 也必须能发自己的消息）；
   - 其余看策略：`off` 从不 / `friends` 看好友 / `allowlist` 看白名单 / `all` 恒真。
5. **按需查询**：好友与白名单查询只在对应策略下发生（`all`/`off` 一次库都不查），
   转发热路径零额外开销 —— 有单测断言"没查"。

## 3. Consequence

- ✅ 用户可控：能表达"不中继 / 只帮朋友 / 只帮这几台 / 全帮"。
- ✅ 默认行为不变 ⇒ 现有功能零风险；语义单一（死开关消失）。
- ⚠️ `friends`/`allowlist` 会**降低可达性**（跨跳投递可能失败）。界面文案必须写清楚
  （已写：每种模式各带一句说明 + 页脚提示默认值）。
- ⚠️ 群聊场景：`friends` 模式下，群成员若不在我的好友列表，我**不会**替它转发。
  这是策略的必然结果，不是 bug；需要"群里都能过"的用户应选 `all`。
- ⚠️ 设置变更需**即时生效**（写入后同步内存缓存，`reset_settings` 也要重置），
  否则会出现"改了设置但行为没变，重启才对"的迷惑现象（已实现并覆盖）。

## 4. 非空转验证（已做）

- 策略真值表（4 策略 × 好友 × 白名单 = 12 组断言）；
- `target` / `ttl<=1` / `sender_is_me` 三条边界× 4 策略；
- `decide_forward` 的按需查询（`all`/`off` 下好友查询计数必须为 0；`friends` 恰好 1 次；
  `allowlist` 不查好友表）；
- `RelayConfig::parse` 对脏 JSON 白名单不 panic、未知策略回落 `all`；
- 「默认策略与今天一致」——任意组合都必须转发。
