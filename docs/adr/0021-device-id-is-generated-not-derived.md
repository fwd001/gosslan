# ADR-0021: 设备 ID 是**生成**的，不是从设备属性派生的

- Status: **Accepted**（2026-09-22，用户真机事故后拍板）
- Date: 2026-09-22
- Owners: Gosslan
- 相关：INV-P11（公钥变更与安全相关）、INV-P21（建链前必须验签对端身份）、
  ADR-0020（公网哑管道中继 —— 它的"支点"就建立在 `device_id → Ed25519` 这层绑定上）、
  ADR-0014（多路径选路里的「大 id 拨、小 id 只接受」镜像规则）

---

## 1. 事故

2026-09-22 早上，同一局域网内两台新装设备的"设备指纹"（设置页 `AboutSection` 那行，实为
`device_id`）**完全相同**，随后出现互相顶号、连不上、日志像网络故障。

## 2. 旧设计为什么会撞

`device_id` 是**派生**的，且派生优先级压过持久化值（`state.rs` 旧 1087-1127 行）：

```text
1. gosslan- + SHA256("gosslan-machine:" ‖ 机器码)[..16]     ← 机器码优先于库里已存的值
2. 库里已持久化的 device_id
3. gosslan- + SHA256("gosslan-host:" ‖ 主机名)[..16]        ← 移动端走这条
```

两条派生路径都可能相同，而**不是"熵不够"**：

| 路径 | 相同的情形 |
|---|---|
| 机器码 | 克隆/未 `sysprep /generalize` 的 Windows 镜像、VM/OEM 模板、PVE 完整克隆、Docker 容器、macOS 迁移助理保下来的 `IOPlatformUUID` |
| 主机名 | 两台新设备的默认主机名相同（`MacBook-Pro.local`、`DESKTOP-ABC123`）；安卓无机器码概念，本就恒走这条 |

而"机器码优先"还多一层坏：本机存过什么都不看 ⇒ 手动改库也改不掉。

## 3. 撞了之后为什么是"打架"而不是"只是难看"

`peers`、`links`、`friends`、`conv_id` 全部按 `device_id` 索引，身份可信度也挂在它上面：

- 两个节点互相覆盖对方的 `peers` 条目；
- Hello 的锚点是"`device_id` → 绑定的 Ed25519"（INV-P21/P11），第二台来连就是一次
  **密钥冲突 ⇒ 硬拒 + 只提示一次**；
- 「大 id 主动拨、小 id 只接受」的镜像规则在 id **相等**时退化（拨号处有
  `peer_id == self.device_id` 的过滤，它会认为"那是我自己"）⇒ 两台互相连不上；
- ADR-0020 的公网中继准入判据是"`friends.ed25519_pubkey` 非空"，同样按 id 索引
  ⇒ 一旦 id 可撞，"锚点绑对了"也无从谈起。

## 4. 决定

```text
device_id = "gosslan-" + hex( SHA256( 首启 16 字节随机 ‖ 机器码 ‖ 主机名 ‖ 排序后的网卡名 )[..8] )
```

1. **唯一性由那次随机数保证**，设备属性只作为额外熵与"同镜像可识别"的线索 —— 属性完全相同
   也不撞（克隆镜像恰恰是属性全等的场景）。
2. **稳定性由"只认持久化值"保证**：只在第一次启动生成一次，此后**绝不重新派生**。
   换网卡、开随机 MAC、重装系统、升级镜像都不会悄悄改掉身份。
3. 形状不变（`gosslan-` + 16 位小写 hex = 24 字符）：昵称由 id 派生、镜像规则要 ASCII 可排序、
   日志与 UI 宽度都按这个形状写着；`device.rs` 的护栏把"前缀只有一个、长度固定、只含小写 hex"
   钉住（2026-09-13 那轮多套一层 `dev-` 导致安卓恒为最小 id、永不主动拨号，教训保留在测试里）。
4. **MAC 与蓝牙地址不进哈希**：`if-addrs` 不跨平台提供 MAC（要写 Win/BSD/Linux 三套系统调用
   加 Android JNI），而 Android/iOS/Windows 默认开 MAC 随机化 ⇒ 加不了唯一性，只会加
   "换网络就换身份"的不稳定。将来要加也只是往属性快照里添一项（见下面"不迁移"的理由）。

## 5. 兼容性与迁移（这条是本 ADR 最要紧的一段）

- **对已装设备完全惰性**：旧代码每次启动都把派生值写回 `settings`，所以已存的值就等于派生值
  ⇒ 换优先级**不改变任何现存设备的 ID**，不打断任何已有好友绑定。这是刻意选的保守面。
- 已经撞上号的那两台，光改生成代码治不了（库里已存的值仍然相同）。处理原则（用户 2026-09-22 定）：
  **其中一台换新 ID；聊天历史不迁移；好友重新添加**。旧会话记录留在本机但不再能继续聊
  （`conv_id` 按旧 id 存）。
- 换 ID 的判据不靠猜：只有当本机观察到"**同一个 `device_id` 带着不同的已验签 Ed25519**"
  时才提示（走 INV-P11 已有的 `key_conflict` 路径），因为无签名 UDP announce 单独不构成证据。
  谁先动手谁换 —— 另一台之后不再看到冲突。
- 允许**自定义后缀**（在现有 ID 尾部加/减字符，上限 = 默认长度 + 3），用于"撞了又不想等"的场景。
  约束：字符集限定小写字母与数字，**不接受空格 / `:` / `/` / `\` / 引号** —— `device_id` 会进日志、
  进 `peer:{id}` 这类拼接键、进诊断面板，任何一处都可能变成注入面。自由文本只给昵称，不给 id
  （id 要参与 ASCII 排序与长度不变量）。

## 6. 没做 / 明说不做

- 不做服务端注册、不做设备认证（KeyMint attestation / DeviceCheck 都要有服务器，与产品定位冲突）。
- 不把 id 当"同一物理设备"的依据：它的语义只是"一次安装"，多开窗口各自成节点（`-i{n}` 后缀）。
- 不引入 MAC / 序列号参与身份：见 4.3。
