## 1. Context

产品定位是"以局域网为主的 mesh，节点互相中继"。但局域网之外有一类真实场景接不上：
家庭宽带与手机网络普遍在 CGNAT 后面，**两侧都没有可被对方直连的公网地址**。

现有能力对这件事的覆盖是残缺的：

| 已有 | 但它解决不了 |
|---|---|
| `PathKind::Routed` + `routed_endpoints`（填 `ip:port` 就拨，10s 一轮，身份由握手学）<br/>`src-tauri/src/network/transport.rs:350-433` | 需要**对端自己有公网地址**。CGNAT 下拿不到 |
| Gossip 洪泛多跳（TTL≤6、fanout=4、按 `target` 定向转发）<br/>`network/transport/gossip.rs:235-301` | 多跳的每一跳都得是**已经连上的 Gosslan 节点**。全网都与外界断开时无路可走 |
| `relay_policy` 中继授权（ADR-0016） | 管的是"节点帮节点转发"，与"有一台机器在中间"无关 |
| 链路优先级 LAN > Routed > Bluetooth，且严格更优才替换<br/>`mesh/selection.rs:30-67` | —（这条正是"局域网能连上时中转自然闲置"的现成实现） |

用户提出的边界（原话要点）：**服务器只管组网**、占用尽量小、**读不到也不存储**、
最多 30 人规模不卡、**对现有功能零破坏**（"只是给接入链路加了一条链路"，类比蓝牙链路），
并且要求按生产可用标准做。

## 2. 先决事实（取证结论，动手前重验）

1. 单聊/群聊正文是端到端加密的，中间节点算出的是另一把密钥 ⇒ **本来就解不开**
   （`crypto.rs:75-102`、`network/transport/gossip.rs:170-221`）。
2. 但**帧的其余部分全是明文 JSON**：`type` 判别符、`device_id`、`from`/`to`、昵称、
   群名册、文件名与大小、已读回执。线格式 = `4B 大端长度 + JSON`，全仓零 TLS
   （`transport/tcp.rs:37-74`）。⇒ "只搬字节的服务器"读不到正文，但**元数据全裸**。
3. `Message::ChatMessage` 直连帧没有信封签名，只靠"链路对端 == `from`"兜（INV-P21）。
   ⇒ 一个能控制这条 TCP 的中间人可以**注入** `Ack`，而 `Ack` 会让发送方删掉 outbox 行。
4. `connect_to_peer` 的链路 key 来自**握手学到的 `device_id`**，不来自 socket 地址
   （`discovery/routed.rs:11` "身份只能来自握手，不能由端点推测"）。
   ⇒ 一条"经过服务器的字节管道"对上层来说与一条直连 TCP **没有区别**。这是本方案能小到这个程度根本原因。
5. `known_id == None` 时拨号按**端点地址**去重（`transport.rs:2118-2142`）
   ⇒ 多台设备共用同一个服务器地址会被压成一条链路。这是必须处理的真坑，不是理论。

## 3. Decision

### D1：采用"每对好友一条哑电路"，不采用消息级邮箱/存储转发

服务器只做两件事：按口令准入、把两条登记了同一通道哈希的 socket 拼成双向字节管道。
它**永远不解析 Gosslan 帧**。

- 为什么这样最小：Gosslan 侧因此可以完整复用既有的 `connect_to_peer` → 签名 `Hello` →
  `verify_hello` → `links` 登记 → `writer_loop`/`reader_loop` 全套。
  **不新增 `Message` 变体、不新增 `kind`** ⇒ 不触发 `WIRE_KINDS`/`MsgKind`/`messageKinds.ts`
  三处同步，不需要 capability 位，不需要 ADR-0007"先铺开再上新帧"的排队，
  **老版本设备只是用不了这条路，其余一切照旧**。
- 邮箱式（服务器按帧里的 `to` 投递、离线代存）被否：服务器必须解析帧才能路由（元数据全暴露，
  与"不读"冲突）、必须落盘（与"不存"冲突）、需要新的确认帧（踩 INV-P24 灰度面）。
  而它唯一的收益"对方离线也能发"，**发送方本地 outbox 已经保留 7 天重投**
  （`db/offline_queue.rs:11-23`），不需要服务器版本。

### D2：会合凭据是"通道哈希"，不是设备 ID

`ch = SHA256("gosslan-relay-ch-v1" ‖ 双方 (device_id, Ed25519 公钥) 按 ID 字典序 ‖ UTC 天数)`。
两端各自算出同一个值、各自拨号注册，服务器只做哈希匹配。

- 服务器看到的是一串 32 字节摘要，还原不出是谁；带 UTC 天数是为了不让"这一对设备"
  变成永久可关联的假名。代价是换天那一刻两侧可能各算一天 —— 每 10s 一轮重拨，几分钟内自愈。
- **这条"自愈"就是全部方案，不做主动双拨**（曾试过按轮交替今日/昨日，已回退）：只有两端时钟
  在零点两侧对不齐时才会算出不同的 day，而对不齐的时长等于**两端时钟偏差**（NTP 下秒级），
  不是指南说的 1 小时；真要做到"同时拨两个 ch"得把在途拨号守卫从 `peer:{id}` 拆成按通道键 ——
  为一个秒级窗口改并发守卫不划算。理由写在 `transport/relay.rs`（`relay_epoch_day` 之后）。
- 排序判据与 `crypto::safety_number` 同源（device_id 恒 ASCII 字典序），保证两端必然一致。

### D3：中继电路**必须**套一层记录封装（`transport/relay_seal.rs`），没有明文兜底

只在走公网中继的链路上启用，局域网/蓝牙/直连跨网段一律不变。

- 协商：双向同时发 `GSRW1 <role> <临时 X25519> <我的 Ed25519> <签名>`，
  签名材料含"**我期望的对端 device_id**"与通道哈希 ⇒ 服务器把我的协商行转给第三人也会失败。
- 验签**只认 friends 表绑定值**（或已 `keys_verified` 的 peers 值），不认协商线自报的公钥。
  这条是整个设计的支点：中继可以伪装成任意地址，但它没有好友的 Ed25519 私钥。
  ⚠️ 支点成立的前提是**那列里的值来路可信**（2026-09-22 补）：`update_friend_pubkeys` 只填空、
  首写者永久胜出，而准入判据 `list_bound_friend_identities` 只看它非空 ⇒ 一次伪造广播抢先
  写进来，就等于"我们主动跨公网给攻击者建电路、还把验签锚在它的钥匙上"。现在三条"成为好友"
  的路径与 `upsert_peer` 问同一道闸（`peer_keys_trusted`），未证明过的来源**只绑加密钥匙、
  锚点留 NULL**，等一次验签通过的 Hello（入站 / 出站 / BLE 三条都打标）补齐。
  判据与理由见 `docs/protocol-invariants.md` INV-P11「锚点是被谁写进去的」。
- 记录 = `nonce(4B 零 ‖ 8B 计数器) ‖ ChaCha20Poly1305(计数器 ‖ 内层帧)`，
  接收端要求计数器**严格 +1** ⇒ 注入、重放、截断一律断链。
  方向密钥两条（`a2b`/`b2a`）不互用 ⇒ 反射失败。
- role 由 device_id 字典序定，**不由"谁先连上"决定**：电路是对称的，若 role 取决于到达顺序，
  两端会算出不同的方向密钥，故障形态是"静默互相解不开"。
- 计数器进明文而不是当 AAD：`crypto.rs` 的 AEAD 全仓不传 AAD，在此单开一条 AAD 路径会造出
  "同一原语两种用法"的第二份真相；进明文同样被标签覆盖，效果一致。
- 不用 TLS：全仓零 TLS 依赖，而这里的身份**已经**是每台设备长期持有的 Ed25519。
  引入证书名与信任链管理，比用已有密钥 + 已有原语大得多，收益却不更高。

### D4：只给"已在 friends 表且公钥已绑定"的对端建中继电路

不给陌生人开放 TOFU 走公网这条新路径。今天"TOFU 未验证也能拿链路、也能被要求转发别人的流量"
（`docs/protocol-invariants.md:330-335`）在局域网里是可接受的，在公网上不是。

### D5：`PathKind` 复用 `Routed`，不新增枚举变体

新增 `PathKind::Relay` 要同时改 `mesh/path.rs` 的稳定字符串、`selection.rs` 的优先级、
`peerConnectionInfo.ts` 的标签、领域图与测试基线 —— 而它今天换不来任何行为差异。
LAN 恒优先于 Routed ⇒ **"填了服务器但当局域网能连时它自然闲置"这条需求由既有代码保证**，
不需要新判据。将来若真要在 UI 上区分"跨网段直连 / 经服务器"，再加 variant（可逆决策）。

### D6：服务器是"可选自托管"，官方不运营

产品一句话从"没有服务器"收窄为
**"没有强制的官方后台：无账号、无注册、无托管服务；跨网是一条可选的自托管哑管道"**。
`AI_RULES.md` §3 相应改写。官方不部署、不持有任何用户数据，因此不构成"有个后台"。

### D7：中继拨号一律带已知 `device_id`（绕开按地址去重）

见 §2.5。`known_id = Some(peer)` ⇒ 去重键是 `peer:<id>`、存在性判据是 `has_endpoint(peer, ep)`，
同一台服务器上的多个好友才能各自拥有一条电路。这条如果不做，故障表现就是"只连得上一个人"，
而且每一轮都静默返回 `AlreadyConnected`。

## 4. Consequences

正面：
- 跨 CGNAT 的可达性从无到有；且**全出站**，不需要打洞、不需要公网 IPv4、不需要域名。
- 对现有链路的改动面：`connect_to_peer` 多一个可选的"经服务器"入参 +
  `TcpSender/TcpReceiver` 多一个可选密封态。局域网/蓝牙代码路径逐字不变。
- 关掉开关 = 行为回到今天，无数据残留（不需要迁移，settings 是 KV 表）。

代价与已知边界（写下来，不要靠"应该没问题"糊过去）：
- 服务器仍看得到：连接时刻、时长、双向字节数、帧的精确长度、同一通道哈希在一天内的重复出现。
  不做填充、不做混淆。
- 服务器可以**断链**（它的工作方式），不能读、不能注入、不能冒充。
- 中继是一条"看起来可达"的持久路径 ⇒ 它静默丢包时，outbox 会按"有链路"的 120s 口径判失败
  （`should_fail_expired_outbox`）。这是既有语义，本轮不改。
- 安卓后台：前台服务未实装 ⇒ 这条链路在安卓上只在应用活着时可靠。
- `Link.endpoint` 在多条中继电路上是**同一个服务器地址** ⇒ 任何"按地址区分连接"的新逻辑都要注意
  （今天 `route_order` 只在单个 peer 的链路列表内按端点对齐，不跨 peer，因此不受影响）。
- 每对好友一条 TCP 连接。30 人全在网外时理论上限 435 条 —— 客户端侧用
  "只给当前无链路的好友建、且带上限"来控制，而不是改服务器。

## 5. 明确不做

TLS / WebSocket / HTTP；帧长度填充；服务器落盘或离线收件箱；多路复用的单一控制连接；
账号/注册/配额；UPnP/NAT-PMP；把 DERP 或 WireGuard 接进来（那是换传输栈，属于另一件事）。

### 实现偏离本 ADR 的一处（改了，因为原计划会更糟）

D1 里写的"settings 三键 + `Settings` 字段 + 五处登记"**没有照做**，改成了独立命令
`get_relay_config` / `save_relay_config`（同 `routed_endpoints` 的形状）。原因不是省事：
前端 `persistSettings()` 把所有偏好打包成**一次** `save_settings` 全量写，把一个需要校验
的字段塞进那个包，非法地址就会让**整次保存失败** —— 用户改的主题/昵称/缓存策略全都存不
下去，而提示只说"地址格式不对"。独立命令的代价是不发 `settings-changed`（另一窗口最多
晚 10s 才看到），远小于上面那个。

### 刻意没做的两件（连同理由，免得下一个人当遗漏）

- **不往 `verify-guards.py` 登记源码文本守卫**：本轮要守的三件事（协商失败必须断链、
  不降级为明文、封套后帧格式不变）**全都是行为**，已经由真实单测钉住；再加一份按源码
  文本判定的守卫就是造出第二个真相源，而本项目已多次为"影子判据"付钱。
- **诊断面板暂不加"中继"那一格**：要做就得往 `AppState` 塞状态，而那个文件与
  `network/transport.rs` 正被并行会话改。当前排障靠 `relay` 主题的日志行（配置已保存 /
  电路已建立 / 建链未成功 / 协商验签失败），它足够定位这类问题。等接线之外的那次
  `AppState` 改动落地时一并补。

只能真机验证、自动化覆盖不到的（须由用户在两台以上设备上确认）：
真实 CGNAT 下的连通与延迟、三端防火墙行为、安卓后台表现、服务器换口令后的失败提示是否读得懂。
