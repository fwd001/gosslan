你现在以 Gosslan v0.12 Stable LAN Chat 为当前目标。

不要继续扩大架构，不要主动实现 Bluetooth、QUIC、mDNS、跨子网、服务端中继、Noise XX、500~1000 节点优化、Mesh 优化或其他未来路线功能。

当前唯一目标：

让现有 LAN Chat 稳定。

验收优先级：

P0：

1. LAN Discovery
2. Friend Request / Accept
3. Online / Offline
4. 双向文本消息
5. msg_id 幂等
6. Outbox
7. Ack
8. Offline resend
9. Network recovery
10. Read Receipt
11. E2EE
12. SQLite persistence
13. Restart recovery
14. Image
15. File
16. Notification
17. 两台真实设备联调

P1：

1. Shared Directory
2. Friend delete/re-add
3. Tray
4. UI 稳定性
5. 基础压力测试

任何涉及消息、网络、协议、E2EE、DB、Outbox、Ack 的修改，必须保护现有 INV-001 ~ INV-008。

不要因为 TCP send 成功就认为消息已送达。
不要绕过 outbox。
不要绕过 msg_id。
不要绕过 Ack。
不要静默吞掉加密错误。
不要让网络临时失败直接变成永久消息失败。

开发策略：

优先复用现有代码。
优先修复现有逻辑。
其次做最小修改。
最后才考虑抽象。

禁止为了一个 Bug 创建第二套逻辑。

不要主动重构 useChatStore、protocol.rs、network、db、crypto。
除非当前 Bug 无法通过局部修改解决。

每修复一个 Bug：

1. 找到真实数据流
2. 找到实际断点
3. 判断根因
4. 做最小修复
5. 增加回归测试
6. 运行相关测试
7. 不通过测试修改测试预期

完成一个任务后至少确认：

npm test
npm run build
cd src-tauri && cargo test --lib
cd src-tauri && cargo check

如果修改网络/协议/消息链路，再运行：

cargo build --example e2e_peer
bash scripts/e2e-dev.sh

最终不要告诉我“理论上应该可以”。

必须告诉我：

* 修改了什么
* 根因是什么
* 做了什么验证
* 哪些验证实际通过
* 哪些验证无法执行以及原因

只有核心 LAN Chat 在两台真实设备上稳定运行，才认为 v0.12 Stable LAN Chat 达标。
